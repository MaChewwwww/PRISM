# PRISM — Functional and Non-Functional Requirements

**One signal. Multiple perspectives. Better decisions.**

This is the requirements baseline for **PRISM**. Priorities use Must/Should/Could. Status is Proposed until its acceptance evidence is reviewed. BA-owned numeric limits are now **authorized** in the [Authorized governance requirements](#authorized-governance-requirements) addendum and in `BUSINESS_RULES.md`; they must be implemented as versioned ruleset configuration, never hard-coded ad hoc. Any limit not covered by that addendum (for example SLOs and backup RPO/RTO) remains **TBD** and must not be guessed in code.

Accepted governance rows are requirements authority, not a claim that every row is release-complete. The stabilization includes sourced IV-rank calculation, option-payoff EV with execution costs, OCC/chain-enriched portfolio concentration, durable audit plumbing, 5-minute autonomous scanning, SEC EDGAR fundamentals ingestion, ShadowFund counterfactual simulation, and weekly Post-Analysis reflection.

### Authorized baseline parameter register

The concrete active values are maintained in `BUSINESS_RULES.md` under [Active baseline parameter register](BUSINESS_RULES.md#active-baseline-parameter-register) and in `backend/app/rules/authorized_baseline.v1.json`. Summary: risk per trade 1.0% normal / 0.75% volatile; target allocation 2.0% normal / <= 1.5% volatile; drawdown states 1.5% / 2.25% / 3.0%; cash buffer >= 10.0%; ticker/sector/cluster concentration <= 25.0% / 50.0% / 40.0%; aggregate modeled hard-stop risk <= 3.0%; maximum open positions 6; maximum bid/ask spread <= 10% of premium; freshness <= 30 seconds; opportunity floor 75 and Balanced 78; net EV >= +0.15R; reward/risk >= 1.5:1; Balanced take-profit 75%; fixed stop-loss 50%; DTE default 7; baseline hold 14 days with a four-trading-day hackathon override. The registry also records the Aug 31 start, Sep 2 entry cutoff, Sep 3 total-equity scoring and force-flatten point, and Sep 4 outer boundary.

## Traceability policy

New behavior must cite one or more requirement IDs in its test name or test metadata. A contract, business-rule, deployment, or security change updates the affected requirement row in the same pull request. Requirements move to Accepted only when the listed evidence exists and the owner approves it.
